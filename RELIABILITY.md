# Поведение шлюза под отказами

Это основной артефакт проекта. Здесь не «работает / не работает», а замеры:
что именно ломается, насколько, и сколько стоит каждый механизм надёжности.

Все числа в таблицах сгенерированы из файлов `bench/results/*.json`, которые
лежат в репозитории рядом с этим документом. Таблицы пересобираются командой
`python -m chaos.report` и руками не правятся.

---

## 1. Как устроен стенд

```
  chaos-харнесс ──HTTP──> llm-gateway ──HTTP──> mock-provider
   (клиент,                (то, что            (три независимых апстрима,
    измеряет)               измеряем)           три диалекта API)
                                │
                                └──> PostgreSQL 16 + pgvector
                                     (лог вызовов, расходы, семантический кэш)
```

**Мок-провайдер** говорит на трёх диалектах — OpenAI (`/v1/chat/completions`),
Anthropic (`/v1/messages`) и Ollama (`/api/chat`) — на трёх независимо
настраиваемых апстримах `/p/primary`, `/p/secondary`, `/p/tertiary`. Поэтому
fallback-цепочка в шлюзе реально пересекает границу диалектов (перевод формата
запроса и ответа), а не просто ходит в три одинаковых URL. Ни одного платного
ключа для этого не нужно.

**Инъекция отказов детерминирована.** Независимые случайные броски давали бы
разброс в несколько процентов на каждом прогоне — ровно тот шум, из-за которого
таблицу итераций невозможно читать. Вместо этого каждый апстрим раздаёт карты
из перемешанной «колоды», собранной из весов профиля и засеянной от
`(seed, upstream, profile)`. За полный проход колоды доли исходов точны, а не
приблизительны, и повторный прогон через месяц раздаст те же карты в том же
порядке.

**Клиентский предел ожидания — 20 с.** Без него наивный шлюз на профиле `hang`
не завершил бы прогон никогда: в этом и смысл базовой строки отчёта.

### Как воспроизвести

```bash
docker compose up -d --build                       # postgres + mock + gateway
python -m chaos.run --label 01_baseline --all      # прогон всех сценариев
python -m chaos.report                             # пересобрать таблицы ниже
```

Любую строку таблицы можно перепрогнать на текущем коде: конфигурация каждой
итерации лежит в `config/iterations/*.yaml` и подключается через
`GATEWAY_CONFIG_OVERLAY`, поэтому «откатываться на старый коммит» не нужно.

```bash
GATEWAY_CONFIG_OVERLAY=config/iterations/01_baseline.yaml docker compose up -d gateway
python -m chaos.run --label 01_baseline --scenario storm
```

| | |
|---|---|
| Железо | 4 vCPU, 15 GB RAM |
| ОС / Python | Ubuntu 24.04, Python 3.12 |
| PostgreSQL | 16.13 + pgvector 0.6.0 |

Абсолютные значения привязаны к этому железу; сравнивать между итерациями
осмысленно, сравнивать с чужими бенчмарками — нет.

## 2. Профили отказов и сценарии

Профиль описывает поведение **одного** апстрима, сценарий раскладывает профили
**по апстримам**. Гоняются сценарии; они же становятся строками таблиц.

| профиль | что делает |
|---|---|
| `healthy` | всё работает, латентность 40–120 мс |
| `rate_limited` | 60% ответов — 429 с заголовком `Retry-After: 1` |
| `flaky_500` | 35% — 500, 15% — 503 |
| `bad_json` | 30% — невалидный JSON при `200 OK`, 20% — валидный JSON без полезной нагрузки |
| `conn_reset` | 50% — обрыв соединения на середине тела ответа |
| `slow` | ошибок нет, латентность 1.5–3 с |
| `hang` | 20% запросов висят 30 с — дольше любого таймаута |
| `storm` | всё сразу: ~70% запросов проблемные |
| `total_outage` | провайдер отвечает 500 на всё |
| `degraded_then_dead` | первые 10 запросов проходят, дальше 100% отказов |

| сценарий | primary | secondary | tertiary | что проверяет |
|---|---|---|---|---|
| `healthy` | healthy | healthy | healthy | контрольная группа: цена самих механизмов |
| `rate_limited` | rate_limited | healthy | healthy | уважение к `Retry-After` |
| `flaky_500` | flaky_500 | healthy | healthy | ретраи на 5xx |
| `bad_json` | bad_json | healthy | healthy | классификация «200 OK, но мусор» |
| `conn_reset` | conn_reset | healthy | healthy | обрыв соединения ≠ ошибка приложения |
| `slow` | slow | healthy | healthy | деградация без ошибок |
| `hang` | hang | healthy | healthy | таймауты |
| `storm` | storm | healthy | healthy | всё сразу |
| `primary_outage` | degraded_then_dead | healthy | healthy | circuit breaker и fallback |
| `total_outage` | total_outage | total_outage | total_outage | пол: когда спасать нечем |

## 3. Что именно измеряется

| метрика | как считается |
|---|---|
| success rate | доля ответов `200 OK`, увиденных клиентом |
| p50 / p95 / p99 | клиентская латентность, nearest-rank (без интерполяции) |
| ретраи | повторные попытки к тому же провайдеру |
| fallback | переходы к следующему провайдеру цепочки |
| CB-пропуски | попытки, отсечённые открытым circuit breaker без похода в сеть |
| кэш-хиты | ответы из семантического кэша |
| стоимость | из таблицы цен по фактическим токенам; сверяется с `GET /v1/usage` |

Клиентская стоимость (сумма заголовков `X-Gateway-Cost-Usd`) и серверная
(дельта по `/v1/usage` из Postgres) считаются независимо и должны совпадать —
это встроенная проверка, что учёт расходов не врёт.

Нагрузка неслучайна по форме: 24 темы по четыре формулировки каждая,
распределение тем — Zipf. На 150 запросах это даёт ~53 уникальных промпта
(64% повторов). Без этого кэш-хит-рейт был бы нулём и ничего не значил.

## 5. Разбор итераций

### Итерация 1 — наивный шлюз (базовая строка)

Один провайдер, без таймаутов, без ретраев, без circuit breaker, без fallback,
без кэша. Логирование в Postgres, учёт расходов и лимит бюджета уже есть — это
функциональные требования, а не механизмы надёжности, и они одинаковы во всех
строках отчёта.

Что видно на базовой строке:

- **Успех = «сколько провайдер соизволил ответить».** Шлюз ничего не добавляет:
  37% на `rate_limited`, 30% на `storm`, 0% на `total_outage`. Каждый отказ
  провайдера — это отказ клиенту, один к одному.
- **`hang` — самый дорогой сценарий, хотя success rate у него 81%.** p95 равен
  ровно клиентскому пределу в 20 с: 20% запросов висят до тех пор, пока клиент
  сам не сдастся. Соединение при этом остаётся занятым и на стороне шлюза —
  один зависший провайдер выедает пул соединений, и отвал начинается у
  запросов, которые сами по себе были бы успешными.
- **`bad_json` (48%) страшнее, чем `flaky_500` (53%).** С точки зрения HTTP это
  успешный ответ, `200 OK` с `Content-Type: application/json`. Без явной
  классификации «распарсилось, но там не ответ» такой сбой утекает в приложение
  как исключение парсера, а не как ошибка провайдера. Здесь он уже отнесён в
  `invalid_response` — иначе метрика была бы не «48% успеха», а «48% успеха и
  непонятное количество пятисоток из глубины кода».
- **`primary_outage` — 6.7%, и это ровно те 10 запросов прогрева**, которые
  профиль пропускает перед смертью апстрима. Все остальные 140 честно ушли в
  мёртвый провайдер: наивный шлюз переоткрывает для себя факт отказа на каждом
  запросе.
- **`slow` — 100% успеха и p95 2.9 с.** Ошибок нет вообще, и именно поэтому этот
  сценарий опасен: мониторинг по кодам ответа его не заметит.

Итог: 50.7% успеха суммарно по всем сценариям, худший сценарий — 0%.
Дальше по одному механизму за итерацию.

## 6. Ограничения

- Все числа получены на моке, а не на живых провайдерах. Это осознанный размен:
  детерминизм и воспроизводимость важнее «настоящности», иначе таблицу нельзя
  было бы сравнивать между итерациями. Реальный провайдер добавит сетевую
  дисперсию и другие распределения латентности, но классы отказов те же.
- Латентности привязаны к конкретному железу (4 vCPU); сравнивайте строки между
  собой, а не с абсолютными значениями из других отчётов.
- Бюджет считается по-репличному: in-memory счётчик сверяется с Postgres.
  Для нескольких реплик нужен общий счётчик (Redis или атомарный инкремент в БД).
- Семантический кэш по умолчанию использует локальный хеш-эмбеддер: он ловит
  повторы и близкие переформулировки, но не настоящую семантику. Что именно он
  ловит — измерено в разделе про кэш.
